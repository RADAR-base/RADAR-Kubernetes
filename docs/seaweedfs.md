# SeaweedFS object storage

RADAR-Kubernetes stores the intermediate and output data (and, if enabled, the database backups) in an S3 object
storage in the cluster. This is minio by default. [SeaweedFS](https://github.com/seaweedfs/seaweedfs) can be used
instead; it is expected to replace minio in a future release.

## Selecting the object storage

Set `object_storage` in `etc/production.yaml`:

```yaml
# 'minio' (default) or 'seaweedfs'
object_storage: seaweedfs
```

With `seaweedfs`, `environments.yaml` loads `mods/seaweedfs.yaml`, which installs SeaweedFS instead of minio and
points the S3 sink connector, `radar-output` and the upload source connector to `http://radar-seaweedfs-s3:8333/`.
The database backups (`cluster.backups.endpointURL` of `cloudnative_postgresql` and the JDBC connectors) also
default to the selected storage, unless an endpoint is set for them.

`environments.yaml` is created from `environments.yaml.tmpl` by `bin/init` only when it doesn't exist. If your
`environments.yaml` is older than the `object_storage` setting, add these lines after the
`- ../mods/confluent_kafka.yaml` line (`helmfile` stops with an error if you select `seaweedfs` without them):

```yaml
    {{ if eq (.Values | get "object_storage" "minio") "seaweedfs" }}
      - ../mods/seaweedfs.yaml
    {{ end }}
```

## What gets deployed

- `seaweedfs-operator`: the [SeaweedFS operator](https://github.com/seaweedfs/seaweedfs-operator), which also
  installs the SeaweedFS CRDs.
- `radar-seaweedfs`: a SeaweedFS cluster of masters, volume servers, filers and S3 gateways, the buckets
  `radar-output-storage`, `radar-intermediate-storage` and `cloudnative-postgresql`, and:
  - the S3 API at `https://api.s3.<server_name>`, with `s3_access_key` and `s3_secret_key` from
    `etc/secrets.yaml` (the same host and credentials as minio's API);
  - the SeaweedFS admin UI at `https://s3.<server_name>`, user `admin` and password
    `radar_seaweedfs.admin.credentials.password` from `etc/secrets.yaml` (generated by `bin/generate-secrets`).

The SeaweedFS filer, master and volume server APIs don't authenticate requests. A network policy only lets other
pods reach the S3 API, the admin UI and the metrics port.

## Configuration

The settings deployers are most likely to change are listed under `radar_seaweedfs` in `etc/base.yaml`; all others
are in the [radar-seaweedfs chart](https://github.com/RADAR-base/radar-helm-charts/tree/main/charts/radar-seaweedfs).
Some things to know:

- **Storage size.** Each volume server gets a PVC of `volume.storage.size` (20Gi). With the default replication
  (`"001"`, one extra copy on another volume server) two volume servers store everything twice, so the usable
  capacity is about one PVC. The chart divides each PVC into `volume.maxVolumes` (32) volumes; every bucket
  takes 2 of them on its first write and more as it fills up. When no volume is free, writes fail, so increase
  the PVC size (or `volume.maxVolumes`, for many small buckets) before that happens. The admin UI shows the
  usage.
- **Extra users**, e.g. read-only access to the output data, are S3 identities:

  ```yaml
  # etc/production.yaml
  radar_seaweedfs:
    s3:
      identities:
        read-output:
          actions: ["Read:radar-output-storage", "List:radar-output-storage"]
  # etc/secrets.yaml
  radar_seaweedfs:
    s3:
      identities:
        read-output:
          credentials:
            accessKey: <access key>
            secretKey: <secret key>
  ```

- **Resources.** With `propose_resource_requests_limits: true`, `mods/resources.yaml` sets requests and limits for
  the SeaweedFS components.

## Existing installations

Switching `object_storage` on an existing installation doesn't copy the data: after the switch, minio is
uninstalled (its PVCs are kept) and the services write to empty SeaweedFS buckets. To keep the data, copy it
first. SeaweedFS can run next to minio by setting `radar_seaweedfs._install: true` while `object_storage` is still
`minio`; its ingresses stay disabled then, because they would use the same host names as minio's. Then:

1. Stop the services that write to the object storage (`radar-s3-connector`, `radar-output`, and the upload source
   connector if installed), e.g. by setting their `replicaCount` to 0.
2. Copy every bucket in the cluster, e.g. with `mc mirror` from a pod running the minio client
   (`cgr.dev/chainguard/minio-client`; the `minio/mc` images can no longer be pulled), using `http://minio:9000`
   and `http://radar-seaweedfs-s3:8333` with `s3_access_key` and `s3_secret_key`.
3. Set `object_storage: seaweedfs`, restore the replica counts and run `helmfile sync`.

This procedure has not been tested on a production installation yet; try it on a test installation first.
